# 传播热度曲线(发酵提醒) 设计文档

> 舆情系统演进 · 子项目 2(投资自用视角)。2026-06-10。

**Goal:** 跟踪同一事件被多少家信源跟进、跟进速度如何,在事件**传播加速(发酵)**时通过
Telegram 主动推「📡 正在发酵」升级提醒,让用户在大事扩散早期就注意到。

**核心事实(代码探查):** 现有 `store.upsert_items` 把"跨刷新重复"(同事件被更多信源再次报道)
**直接跳过丢弃**——这恰是传播信号本身。本设计先把信号留住,再做档位与提醒。

---

## 锁定的设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 核心用途 | 发酵提醒(推送) | 最贴近持仓决策;曲线图/排序加权留后续 |
| 提醒范围 | 重要事件 + 自选相关 | `llm_importance ≥ 7` **或** 命中 watchlist;信噪比最高 |
| 提醒次数 | 每档升级一次 | 能看到事态升级但不被轰炸;降档不提醒 |
| 信号存储 | mentions 流水表(方案A) | 信号真实完整;为后续曲线图留数据地基 |
| 传播指标 | 滚动窗口内**不同来源数** | 同源刷屏只算 1,防单源噪音 |

## 数据模型

`store.py` 新表(随 `init_db` 建):

```sql
CREATE TABLE IF NOT EXISTS mentions (
    group_key TEXT,      -- 归属事件簇(items.dedup_group)
    source    TEXT,      -- 提及来源(如 新浪财经 / Bloomberg)
    title_zh  TEXT,      -- 该信源首报标题(留痕,供回放/调试)
    ts        TEXT,      -- 该信源首报时间(CST ISO)
    PRIMARY KEY (group_key, source)   -- 事件×信源 首见才记一行,INSERT OR IGNORE 幂等
);
CREATE INDEX IF NOT EXISTS idx_mention_ts ON mentions(ts);
```

> 实现修正(2026-06-10 规划期):语义为「每个事件簇,每家信源,记**首报时间**一行」。
> 同源重发/重复抓取天然不重复计;传播曲线 = 各信源加入时间的累积。
> 原设计的 `items.prop_level` 列**取消**——mentions 表即持久化,重启后 `refresh()`
> 必然先从 mentions 重算,列是冗余(YAGNI)。

### upsert_items 行为变更

所有路径统一调用 `_record_mentions`((group, source) 已存在则忽略):

| 情形(现有行为) | 新行为 |
|---|---|
| 全新条目 → 插入 | 插入 + 按 `also_sources`(单轮聚类合并的各家,缺省=自身 source)逐家记 mention |
| 新 id 但 dedup_group 已存在 → 跳过 | 仍跳过,记 mention(归该 group) |
| 标题相似命中近窗条目 → 跳过 | 仍跳过,记 mention(归**被命中条目**的 group;`recent_feats` 由"仅特征"改为"(特征, group)"元组) |
| 同 id 再次抓到 → 更新可变字段 | **也记**——`_cluster` 在单轮内就把同事件并成代表条目,跨轮新增信源体现为同 id 条目的 `also_sources` 增长,不记会丢信号;(group,source) 唯一保证幂等 |

mentions 随现有 `prune()` 同窗口(默认 30 天)清理。

## 传播档位(server 侧计算)

每轮刷新后,对窗口内活跃 group 统计**滚动 90 分钟内 `COUNT(DISTINCT source)` = n**:

| 档位 | 名称 | 默认阈值 |
|---|---|---|
| LV1 | 发酵 | n ≥ 3 |
| LV2 | 升温 | n ≥ 5 |
| LV3 | 沸腾 | n ≥ 7 |

- 环境变量可配:`PROP_WINDOW_MIN`(默认 90)、`PROP_LEVELS`(默认 `3,5,7`)
- 窗口统计 = 窗口内**首报**的信源数(发酵=加速,老事件信源齐了但无新加入 → 档位自然回落,降档不提醒)
- 结果挂代表条目:`it["propagation"] = {"level": L, "sources": n, "window_min": w}`(window_min 供 bot 渲染)
- 随现有 `/api/public/items` 自然带出,**不加新端点**;重启恢复靠 mentions 表重算,不另落库

## 发酵提醒(bot 侧)

推送轮询(现有 push loop)中,对带 `propagation` 的条目:

- **触发**:`level` > `bot_state.json["prop_alerted"].get(group, 0)`
- **门槛**:且(`llm_importance ≥ 7` 或 实体/`sentiment.tgt` 命中 watchlist)
- **动作**:推卡片——复用 `render_push_item`,头部上方加一行
  `📡 <b>正在发酵 · LV2</b>(90分钟内5家信源跟进)`(块间空行风格与 2026-06-10 排版一致)
- **记账**:`prop_alerted[group] = level`;每档一次,降档不提醒;条目过期随 state 清理

## 边界与降级

- **LLM 关闭**:重要度条件不可用 → 门槛退化为"仅自选命中";发酵信号本身不依赖 LLM,不报错
- **单源刷屏**:按不同来源数计,同源窗口内多次提及只算 1
- **华尔街见闻多频道**:`source` 同名只算 1 家(符合"不同信源"语义)

## 不在本期范围(MVP 边界)

- 网页端热度曲线图(mentions 数据已可回放,后续子项目)
- 发酵事件在精选/突发流的排序加权(后续在 `_score` 加一项即可)
- 跨事件簇合并(两个 group 实为同一事件)→ 依赖现有去重质量,不另做

## 测试(TDD,stdlib unittest)

1. `store`:四种 upsert 情形——新条目记首条 mention;同 group 跳过仍记;相似标题跳过记到**对方** group;同 id 更新不记
2. 档位:窗口内 n 个不同来源 → 对应 LV;窗口外提及不计;同源多次只算 1
3. `bot`:升档+重要 → 推且头部含「📡 正在发酵」;同档不重推;升档但不重要且未命中自选 → 不推;LLM 关时自选命中仍推
4. `prune` 连带清理超期 mentions

## 风险

- **去重质量决定信号质量**:相似标题归簇错了,mention 会记错 group——沿用现有 `DEDUP_SIM=0.5`,不在本期调
- **阈值冷启动**:3/5/7 是拍的,跑几天看实际分布再调(已留环境变量)
- **bot/server 双进程**:信号只经 items API 传递,bot 不直接读库,保持现有边界
